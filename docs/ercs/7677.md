# ERC-7677 — Paymaster RPC protocol

> [eips.ethereum.org/EIPS/eip-7677](https://eips.ethereum.org/EIPS/eip-7677)

The dapp-side protocol for ERC-4337 paymasters. Two RPC methods (`pm_getPaymasterStubData` and `pm_getPaymasterData`) split the sponsor's commitment into a stub call (so the bundler can estimate gas against realistic limits) and a final call (the real signed payload). The library binds both methods plus a small `apply_to_user_op` helper that merges a paymaster response onto a v0.7 `UserOperation`.

```ts
import { parse } from "valibot";
import { BytesSchema, UintSchema } from "@ethernauta/core";
import {
  ENTRY_POINT_V07_ADDRESS,
  type UserOperation,
} from "@ethernauta/eip/4337";
import {
  apply_to_user_op,
  pm_getPaymasterStubData,
  pm_getPaymasterData,
} from "@ethernauta/erc/7677";
import { http } from "@ethernauta/transport";

declare const draft: UserOperation;
const chainId = parse(UintSchema, "0xaa36a7"); // Sepolia
const paymaster_url = "https://api.pimlico.io/v2/sepolia/rpc?apikey=…";

// Stub: dummy paymasterData (same byte length as the real signature) +
// realistic paymasterVerificationGasLimit + paymasterPostOpGasLimit.
const stub = await pm_getPaymasterStubData({
  userOp: { /* v0.6 or v0.7 shape */ ...draft, initCode: parse(BytesSchema, "0x") },
  entryPoint: ENTRY_POINT_V07_ADDRESS,
  chainId,
})(http(paymaster_url));

const with_stub = apply_to_user_op(draft, stub);
// → run `eth_estimateUserOperationGas` against `with_stub` here

// Final: real paymaster signature over the final UserOp shape.
const final = await pm_getPaymasterData({
  userOp: { /* same shape, refined gas */ ...with_stub, initCode: parse(BytesSchema, "0x") },
  entryPoint: ENTRY_POINT_V07_ADDRESS,
  chainId,
})(http(paymaster_url));

const ready = apply_to_user_op(with_stub, final);
// → `ready` is now signable and submittable via @ethernauta/eip/4337
void ready;
```

## Why the two-call pattern

The v0.7 userOpHash depends on the paymaster fields, and the bundler's `eth_estimateUserOperationGas` needs realistic gas limits to estimate against. If the paymaster only signed once, the round-trip would need the paymaster to commit before the client knew the final gas — circular dependency. Stub + final breaks the cycle:

1. **Stub** returns dummy `paymaster` + `paymasterData` (same byte length as the real signature, so estimation matches the real path) plus realistic gas limits.
2. The client estimates gas via the bundler against the stubbed shape.
3. **Final** returns the real `paymaster` + `paymasterData` for the now-finalised UserOp shape. The paymaster has committed.

## Surface

### RPC bindings

| Export | Resolver | Purpose |
|---|---|---|
| `pm_getPaymasterStubData` | `Http` | Stub call. Returns dummy paymaster + real gas limits. |
| `pm_getPaymasterData` | `Http` | Final call. Returns the real signed paymaster payload. |

Both bindings take an `Http` transport directly (paymasters are JSON-RPC-over-HTTP endpoints separate from the bundler). No factory wrapper.

### Schemas (v0.6 + v0.7)

| Schema | Purpose |
|---|---|
| `PaymasterUserOperationSchema` | Union over `V06` (`initCode`) and `V07` (`factory` + `factoryData`). v0.6 first so its required `initCode` discriminates correctly. |
| `PaymasterStubDataSchema` | Union over `V07` (`paymaster` / `paymasterData` / gas limits / optional `sponsor` / `isFinal`) and `V06` (packed `paymasterAndData`). v0.7 first. |
| `PaymasterDataSchema` | Same shape as stub minus the gas limits and `isFinal` / `sponsor` flags. |
| `ContextSchema` | Opaque `record(string, unknown)` — the paymaster-defined opaque blob that round-trips through both calls. |
| `SponsorSchema` | `{ name, icon? }`. |

The v0.6 / v0.7 union ordering matters: v0.7 is first in the response unions because its required-key set is the stricter superset; v0.6 is first in the request union because its required `initCode` is the only field that discriminates on the input side.

### Composition

| Export | Purpose |
|---|---|
| `apply_to_user_op` | Merge a stub or final response onto a v0.7 `UserOperation`. v0.6 responses throw — the packed `paymasterAndData` shape has no slot in the v0.7 schema. |

## v0.6 callers

ERC-7677 supports v0.6 EntryPoints. The schemas parse v0.6 payloads but `apply_to_user_op` only handles v0.7 — v0.6 callers compose `pack_paymaster_and_data` from `@ethernauta/eip/4337` manually.

## A note on scope

ERC-7677 binds the dapp side of the paymaster protocol. The library does not run a paymaster (that's a separate service stack — same M4 reasoning as the bundler). Any ERC-7677-compliant paymaster (Pimlico, Alchemy, Biconomy, self-hosted) works.

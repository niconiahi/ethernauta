# EIP-5267 — Typed-data domain getter

> [eips.ethereum.org/EIPS/eip-5267](https://eips.ethereum.org/EIPS/eip-5267)

EIP-5267 lets a contract self-describe its EIP-712 domain. Instead of hard-coding the `name`, `version`, `chainId`, `verifyingContract`, and `salt` on the dapp side, you call `eip712Domain()` on the contract and the contract tells you. The returned seven-tuple includes a `bytes1 fields` bitmap that signals which of the five domain members are actually populated.

```ts
import { parse } from "valibot";
import { AddressSchema, BytesSchema } from "@ethernauta/core";
import { get_domain } from "@ethernauta/eip/5267";
import { eth_call } from "@ethernauta/eth";
import { contract, create_reader, encode_chain_id, http } from "@ethernauta/transport";
import { eip155_1 } from "@ethernauta/chain/eip155-1";

const CHAIN_ID = encode_chain_id({ namespace: "eip155", reference: eip155_1.chainId });
const reader = create_reader([
  { chainId: CHAIN_ID, transports: [http("https://ethereum-rpc.publicnode.com")] },
]);

const token = parse(AddressSchema, "0x4c9edd5852cd905f086c759e8383e09bff1e68b3"); // Ethena USDe

const callable = get_domain()(contract({ chain_id: CHAIN_ID, to: token }));
const bytes = await eth_call([{ to: callable.to, input: callable.data }])(
  reader({ chain_id: CHAIN_ID }),
);
const { domain, extensions } = callable.decode(parse(BytesSchema, bytes));
void domain;
void extensions;
```

The decoded `domain` is the same `TypedDataDomain` shape `@ethernauta/eip/712` accepts — members that are zero in the bitmap are dropped entirely, so it can be fed straight back into `eth_signTypedData_v4` without manual cleanup.

## Surface

| Export | Type | Purpose |
|---|---|---|
| `get_domain` | `() => (ContractContext) => Callable<DomainResult>` | Build the calldata, decode the seven-tuple, drop omitted members. |
| `DomainResult` | `{ domain: TypedDataDomain, extensions: Uint256[] }` | The decoded payload. |
| `decode_fields` | `(0x${string}) => DomainFields` | Decode the `bytes1` bitmap into five booleans. |
| `FIELD_NAME`, `FIELD_VERSION`, `FIELD_CHAIN_ID`, `FIELD_VERIFYING_CONTRACT`, `FIELD_SALT` | constants | Bit masks for the five domain members. |

## Composing with EIP-712

The dapp orchestrates: fetch the domain via 5267, sign with 712, without ever hard-coding the domain fields.

```ts
import { parse } from "valibot";
import { AddressSchema, BytesSchema } from "@ethernauta/core";
import { eth_signTypedData_v4 } from "@ethernauta/eip/712";
import { get_domain } from "@ethernauta/eip/5267";
import { eth_call } from "@ethernauta/eth";
import { contract, create_provider, create_reader, encode_chain_id, http } from "@ethernauta/transport";
import { eip155_1 } from "@ethernauta/chain/eip155-1";
import type { Provider } from "@ethernauta/eip/1193";

const CHAIN_ID = encode_chain_id({ namespace: "eip155", reference: eip155_1.chainId });
declare const provider: Provider;
const reader = create_reader([
  { chainId: CHAIN_ID, transports: [http("https://ethereum-rpc.publicnode.com")] },
]);
const { signer } = create_provider(provider);

const token = parse(AddressSchema, "0x4c9edd5852cd905f086c759e8383e09bff1e68b3");
const account = parse(AddressSchema, "0x70997970C51812dc3A010C7d01b50e0d17dc79C8");

const callable = get_domain()(contract({ chain_id: CHAIN_ID, to: token }));
const bytes = await eth_call([{ to: callable.to, input: callable.data }])(
  reader({ chain_id: CHAIN_ID }),
);
const { domain } = callable.decode(parse(BytesSchema, bytes));

const signature = await eth_signTypedData_v4([
  account,
  {
    domain,
    types: { Permit: [{ name: "owner", type: "address" }] },
    primaryType: "Permit",
    message: { owner: account },
  },
])(signer({ chain_id: CHAIN_ID }));
void signature;
```

This is the M3 composition pattern — `@ethernauta/eip/712` does not gain a parallel "fetch domain from contract" code path; the dapp wires the read into the sign.

## Where this gets used

- **Modern OZ-based ERC-20s.** OpenZeppelin Contracts v4.8+ ships `eip712Domain()` via the `EIP712Upgradeable` mixin. USDe, Lido contracts, and most post-2022 deployments implement it.
- **Permit flows that survive proxy upgrades.** If the implementation changes its `name` or `version` after an upgrade, a hard-coded domain breaks; fetching it via 5267 keeps signing correct across upgrades.
- **Cross-chain replays.** The bitmap distinguishes "no chainId field" (intentional cross-chain typed data) from "chainId is 1" — useful when normalising messages across chains.

Older deployments (USDC, USDT, DAI) predate EIP-5267 and the call will revert. Catch and fall back to hard-coded domain values for those contracts.

# The wallet — @ethernauta/wallet

The wallet is a Manifest V3 Chrome extension whose job is to hold an encrypted mnemonic in IndexedDB and respond to JSON-RPC-shaped sign requests from dapps. It is **private** in the workspace (`packages/wallet/package.json:5`) — it ships as `extension.zip`, never to npm.

The mental model is small once internalized: every interaction is a four-hop **request / response** between a webpage, a content script, the background service worker, and a popup; the popup picks a view based on the request method, validates the request with a Valibot schema, and lets the user approve or reject.

## The three execution contexts

A Chrome MV3 extension runs in three places. Each lives in its own file under `packages/wallet/`:

| Context | Entry | Lifetime | Role |
|---|---|---|---|
| Content script | `packages/wallet/manifest/browser.entry.ts` | Per-tab, injected at `document_end` | Bridge — translates `window.postMessage` from the page into `chrome.runtime.sendMessage` to the background, and back |
| Background service worker | `packages/wallet/manifest/extension.entry.ts:1-135` | Event-driven, killed when idle | Router — stashes the request in `chrome.storage.session`, opens the popup, waits for the popup-ready notification, replays the request to the popup, then routes the response back to the originating tab |
| Popup (UI) | `packages/wallet/src/entry.preact.tsx` → `controller.tsx` | While the popup window is open | View — Preact app that authenticates the user, decrypts the vault, renders a view per request method, and posts back the response |

The page itself (`window`) is the fourth participant, but it is not extension code — it is the dapp, talking to the wallet via the `@ethernauta/transport` `create_signer` resolver. The dapp never sees a provider object; the signer just `postMessage`s and waits.

## The message envelope

All wallet ↔ dapp traffic flows through a single Valibot-validated envelope. The schemas live in `packages/wallet/src/utils/event.ts`. The convention (read `skills/conventions/SKILL.md`):

```ts
// packages/wallet/src/utils/event.ts:18-30
export const SignTransactionRequestSchema = object({
  id: string(),
  type: literal("ETHERNAUTA_REQUEST_SIGN_TRANSACTION"),
  method: string(),
  chainId: string(),
  to: optional(string()),
  params: optional(
    union([array(unknown()), record(string(), unknown())]),
  ),
})
export type SignTransactionRequest = InferOutput<
  typeof SignTransactionRequestSchema
>
```

- Every message is `{ id, type, ... }`.
- `type` is one of `ETHERNAUTA_REQUEST_*`, `ETHERNAUTA_RESPONSE_*`, `ETHERNAUTA_NOTIFICATION_*`. The prefix is how the background router decides which branch to take (see `extension.entry.ts:41` / `:103` / `:124`).
- `id` is a UUID generated by the dapp; it ties a response back to its request.
- `params` is left as `array(unknown()) | record(string(), unknown())` at the envelope layer. The popup, after dispatching by `request.method`, re-parses `params` with the method's own schema (`TypedDataSchema`, `AddEthereumChainParameterSchema`, `SendCallsParameterSchema`, `SendSetCodeTransactionParametersSchema`). See `controller.tsx:60-130`.

When introducing a new message: add a `*Schema` in `event.ts`, derive the type, **never** hand-write the interface.

## The request lifecycle (signing flow)

End-to-end, for an `eth_signTransaction` originating in the dapp:

1. **Dapp** calls a method (e.g. `eth_signTransaction(...)(signer({ chain_id }))`). The signer `postMessage`s an `ETHERNAUTA_REQUEST_SIGN_TRANSACTION` to `window`.
2. **Content script** picks it up and forwards via `chrome.runtime.sendMessage`.
3. **Background** (`extension.entry.ts:38-101`):
   - `parse(EthernautaEventSchema, message)` — every message is validated.
   - Stashes `{ tab_id, request }` under `pending_<id>` in `chrome.storage.session`.
   - Opens the popup (`chrome.action.openPopup()`).
   - Listens once for `ETHERNAUTA_NOTIFICATION_POPUP_READY` from the popup, then replays the original request to it via `chrome.runtime.sendMessage`.
4. **Popup** (`controller.tsx:36-143`):
   - `useEffect` connects to background, dispatches `POPUP_READY`, and registers an `onMessage` listener.
   - On receiving the request: `parse(EthernautaRequestSchema, message)`, then `is_authenticated()` + `validate_vault()`. If not authenticated, the popup short-circuits to the password view; user enters password, vault is decrypted, the request is replayed.
   - Routes by `request.method` to a view-state signal + sets `view.value`. The view renders, the user approves/rejects, the view posts back an `ETHERNAUTA_RESPONSE_*`.
5. **Background** (`extension.entry.ts:103-122`):
   - Sees the response type prefix, parses it, looks up `pending_<id>` to find the originating `tab_id`, forwards the response to that tab.
   - Removes the pending entry.
6. **Content script** posts the response back to `window`. The signer in the dapp resolves its promise.

If the popup window closes mid-flow, the background `onConnect`/`onDisconnect` handler (`extension.entry.ts:19-36`) walks every `pending_*` entry, sends an `ETHERNAUTA_RESPONSE_NATIVE_EXTENSION_CLOSE` to each, and clears them. This is how the dapp learns the user dismissed the popup without clicking either button — the signer surfaces it as an EIP-1193 `{ code: 4001, message: "Extension closed" }`.

## View routing — single signal

The popup is a single Preact component driven by one signal. `packages/wallet/src/utils/view.ts:1-5`:

```ts
import { signal } from "@preact/signals"

export const INITIAL_VIEW = "password"
export const view = signal(INITIAL_VIEW)
```

`controller.tsx:147-186` is the entire router — a `switch` on `view.value` returning a view component. To add a new view: write the component, add a case, and set `view.value = "your-view"` from the relevant request handler.

The current view set (each backed by a folder under `packages/wallet/src/views/`):

| view value | When | What |
|---|---|---|
| `"password"` | Default; vault exists, not yet authenticated | Password entry, derives PBKDF2 key, decrypts vault |
| `"mnemonics"` | No vault exists | Initial setup — generate / import a mnemonic, set password, create vault |
| `"wallet"` | Authenticated, no pending request | Idle home — balance, chain switcher |
| `"connect"` | `eth_requestAccounts` arrived | Approve / reject account exposure |
| `"sign"` | Generic `eth_signTransaction` arrived | Approve / reject EIP-1559 transaction |
| `"sign-typed-data"` | `eth_signTypedData_v4` arrived | EIP-712 typed-data approval |
| `"personal-sign"` | `personal_sign` arrived | EIP-191 personal-message approval |
| `"add-chain"` | `wallet_addEthereumChain` arrived | Approve / reject chain addition |
| `"authorize-delegation"` | `wallet_sendSetCodeTransaction` arrived | EIP-7702 delegation approval |
| `"send-calls"` | `wallet_sendCalls` arrived | EIP-5792 batched-calls approval (sequential strategy; see EIP-5792 section below) |
| `"select-chain"` | User-initiated | Switch active chain |

The request signals (`transaction_request`, `connection_request`, `typed_data_request`, `personal_sign_request`, `add_chain_request`, `send_calls_request`, `set_code_request`) live in `packages/wallet/src/utils/transaction.ts` and each has its own Valibot-derived type. The view reads its signal to know what to render, and the user's click handler posts the matching `ETHERNAUTA_RESPONSE_*` back.

## EIP-5792 — batched calls

The wallet implements `wallet_sendCalls` / `wallet_getCallsStatus` / `wallet_getCapabilities` (schemas + method bindings in `@ethernauta/eip/5792`). This is the surface dapps use for any multi-call flow; **dapps do not track underlying transaction hashes themselves** — the wallet owns batch lifecycle and transaction-hash tracking under the hood.

**v1 strategy: sequential EOA sends.** When `wallet_sendCalls` arrives, the popup renders `views/send-calls/`. On approval, each call is encoded as its own EIP-1559 transaction with consecutive nonces and broadcast via `eth_sendRawTransaction`. A bundle id is minted (`utils/calls-registry.ts`) and the `bundle_id → transaction_hashes` mapping is persisted in `chrome.storage.session`. The wallet rejects requests with `atomicRequired: true` — `wallet_getCapabilities` honestly reports `atomic: { status: "unsupported" }` per chain so dapps that branch on capabilities will degrade gracefully.

**Chain pinning.** The send-calls view rejects a batch whose `chainId` differs from the wallet's currently `selected_chain`. The user is asked to switch chains in the wallet and retry — the dapp's chain id is informational, not a switch command.

**On-demand status, not continuous tracking.** `wallet_getCallsStatus(bundle_id)` is answered by the background entry (`extension.entry.ts` — no popup) by snapshot-polling `eth_getTransactionReceipt` for each transaction hash in the bundle and composing a `CallsStatus`. There is no `chrome.alarms`-driven background watcher. MV3 service workers cannot run long-lived loops; status is computed per request. A continuous tracker with badging is a possible v3 enhancement and is deferred indefinitely.

**Atomic execution (v2, future).** EIP-7702 will replace the sequential strategy on chains where a deployed `BatchExecutor` delegate exists. The wire protocol does not change — only `wallet_getCapabilities` flips to `atomic: { status: "supported" }` and the broadcast path switches to a single `0x04` transaction. Dapps written against v1 keep working.

## Security boundary

The single trust boundary is the vault. `packages/wallet/src/utils/vault.ts`:

- Mnemonic is encrypted with AES-GCM. The encryption key is derived from the user's password via PBKDF2 (100,000 iterations, SHA-256). Salt and IV are random per write.
- The encrypted record (`{ salt, iv, cipher }`, all base64) is stored in IndexedDB at `ethernauta/signer`, store `vault`, key `credentials`.
- The decrypted mnemonic is held in memory inside `wallet.signal` only while the popup is open and authentication has not expired.
- Authentication is timestamp-based with a 5-minute window (`packages/wallet/src/utils/authentication.ts:20-32`). On each request, the popup checks `is_authenticated()`; if false, it routes to `"password"` to re-derive the key.

Constraints that must not slip:

1. **The mnemonic and private key never leave the popup process.** Not over `postMessage`, not over `chrome.runtime`, not into a log.
2. **The vault is the only persistent secret store.** No private key, mnemonic, or seed is ever written to `chrome.storage.*`. `chrome.storage.local` holds only the auth timestamp.
3. **Every inbound message is `parse`d at the envelope layer before anything else.** Don't trust message shape.
4. **The signer surface in `@ethernauta/eip` and `@ethernauta/eth` is the only protocol surface the wallet must respect.** When adding a new RPC method handler in the wallet, add the matching schema in `event.ts` (or import it from the relevant `@ethernauta/eip/<n>` package), add a request signal in `transaction.ts`, add a view, and wire the `controller.tsx` switch.

## Interacting with the wallet from a dapp

This is consumer territory — the `ethernauta` skill (`skills/ethernauta/SKILL.md`) is the long form. The short form:

```ts
// 1. Request accounts (opens the connect view in the popup)
import { eth_requestAccounts } from "@ethernauta/eip/1102"
import { create_signer } from "@ethernauta/transport"

const signer = create_signer({ chains: [{ chainId: SEPOLIA }] })
const [account] = await eth_requestAccounts()(
  signer({ chain_id: SEPOLIA }),
)

// 2. Sign + broadcast a native transfer
import { eth_signTransaction, eth_sendRawTransaction } from "@ethernauta/eth"
import { number_to_hex } from "@ethernauta/utils"

const signed = await eth_signTransaction([
  { to: recipient, value: number_to_hex(1n) },
])(signer({ chain_id: SEPOLIA }))

const hash = await eth_sendRawTransaction([signed])(
  writer({ chain_id: SEPOLIA }),
)
```

The wallet does not expose a provider object. The connection is the `postMessage` channel that the signer opens transparently. There is nothing global to detect — if the extension is installed, the channel works; if not, the signer rejects with `{ code: 4001, message: "Extension closed" }`.

## Adding a new RPC method to the wallet — checklist

1. **Schema.** Either reuse a schema from `@ethernauta/eip/<n>` (the spec package — see `eip` skill), or add a new one in `packages/wallet/src/utils/event.ts` for envelope shape and `packages/wallet/src/utils/transaction.ts` for the popup-side request signal. Derive types with `InferOutput`.
2. **Route.** Add a branch in `packages/wallet/src/controller.tsx:42-140` that matches on `request.method`, `parse`s the params, sets the request signal, and sets `view.value`.
3. **View.** Add a folder under `packages/wallet/src/views/<view>/` with `index.tsx`. The view reads its request signal, renders an approve/reject UI, and posts back an `ETHERNAUTA_RESPONSE_*`.
4. **Response schema.** Define the response message in `event.ts` if the wallet needs to send a new type back. Otherwise reuse `SignTransactionResponseSchema` (it carries an opaque string payload).
5. **Background.** Usually no change — the background router is method-agnostic; it just routes by id. Touch `extension.entry.ts` only if the method has special background-only handling (e.g. `wallet_getCapabilities` / `wallet_getCallsStatus`, which the background answers directly without ever opening the popup — `extension.entry.ts:48-72`).
6. **Tests.** Add a `*.test.ts` next to the new utility, mocking `chrome.runtime` and IndexedDB via `fake-indexeddb` (see `packages/wallet/src/utils/vault.test.ts` for the pattern).

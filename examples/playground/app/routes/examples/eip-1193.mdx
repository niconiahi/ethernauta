# EIP-1193 — provider as transport facade

EIP-1193 specifies the envelope (`request`, the event
emitter, the five wallet error codes) and nothing about
which methods exist. Method existence comes from other
EIPs (1474, 1102, 2255, 3085, 3326, 191, 712, 5792, 7702).

Ethernauta provides one dapp-side adapter for any 1193
source — an EIP-6963 announce, `window.ethereum`, a test
mock — that lifts it into the same `method(args)(transport)`
shape used everywhere else in the library.

- **`useProviderDetail({ key })`** — React hook that runs
  the EIP-6963 announce dance and rehydrates the user's
  previously-picked wallet from a caller-owned storage key.
  Returns the live `EIP6963ProviderDetail` (`info` +
  `provider`) or `null` while no wallet is picked. Use this
  when you also need the raw 1193 provider (for
  `watch_accounts` / `watch_chain`, or to read `info.name`
  / `info.icon`).
- **`useProvider({ key })`** — convenience composition of
  `useProviderDetail` + `create_provider`: returns a
  ready `{ provider_detail, reader, signer }` so callers
  that only need the resolver pair skip the `create_provider`
  step. `null` until the announce dance resolves.
- **`create_provider(provider)`** — wraps any 1193 provider
  into a factory with `.signer({ chain_id })` for
  `Signable<T>` methods and `.reader({ chain_id })` for
  `Readable<T>` methods. Same call shape as
  `create_signer(CHAINS)` / `create_reader(CHAINS)` — only
  the transport-construction line differs.
- **`watch_accounts` / `watch_chain`** — typed wrappers
  over `provider.on("accountsChanged" | "chainChanged", …)`
  that validate the payload before invoking the handler.

## The code

```tsx
import {
  eth_chainId,
  eth_getBalance,
} from "@ethernauta/eth"
import { eth_requestAccounts } from "@ethernauta/eip/1102"
import {
  watch_accounts,
  watch_chain,
} from "@ethernauta/eip/1193"
import { useProviderDetail } from "@ethernauta/react"
import {
  create_provider,
  encode_chain_id,
} from "@ethernauta/transport"

// The injected provider routes everything through the
// wallet's selected chain, so the resolver context is just
// a well-formed CAIP-2 id to bootstrap the first read.
const DISCOVERY_CHAIN_ID = encode_chain_id({
  namespace: "eip155",
  reference: 1,
})

// `useProviderDetail` runs the 6963 announce dance and
// rehydrates the persisted wallet. `null` until resolved.
const provider_detail = useProviderDetail({
  key: "my-app:picked-rdns",
})
if (!provider_detail) return <Picker />

// One factory call. Same provider, both shapes.
const provider = create_provider(provider_detail.provider)

// Readable: ask the wallet which chain it's on. Same
// `method(args)(resolver)` shape as every other read.
const current_hex = await eth_chainId()(
  provider.reader({ chain_id: DISCOVERY_CHAIN_ID }),
)
const chain_id = encode_chain_id({
  namespace: "eip155",
  reference: Number.parseInt(current_hex, 16),
})

// Signable: ask the wallet for accounts.
const accounts = await eth_requestAccounts()(
  provider.signer({ chain_id }),
)

// Readable: route eth_getBalance through the wallet's
// selected RPC. The method doesn't know it's going through
// a wallet — the resolver shape is the same as a public-RPC
// reader.
const [first] = accounts
if (first) {
  const balance = await eth_getBalance({ address: first })(
    provider.reader({ chain_id }),
  )
}

// Reactively watch updates from the injected provider.
watch_accounts(provider_detail.provider, (next) => {
  // re-render with `next`
})
watch_chain(provider_detail.provider, (next) => {
  // re-render with `next` (hex chain id)
})
```

## The two paths, side by side

The same `eth_getBalance` call works against a public RPC
with no wallet — just swap the transport:

```ts
import { create_reader, http } from "@ethernauta/transport"

const reader = create_reader([
  {
    chainId: "eip155:1",
    transports: [http("https://ethereum-rpc.publicnode.com")],
  },
])
const balance = await eth_getBalance({ address })(
  reader({ chain_id: "eip155:1" }),
)
```

`create_provider(provider).reader({ chain_id })` and
`create_reader(CHAINS)({ chain_id })` produce structurally
the same `ResolvedReader`. The method doesn't know which one
it's running against — that's the point.

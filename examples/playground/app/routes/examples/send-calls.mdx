# ERC-5792 — batched calls via `wallet_sendCalls`

End-to-end ERC-5792 flow on Sepolia. The dapp asks the
wallet to send a batch of calls; the wallet returns a
batch id immediately, then the dapp polls
`wallet_getCallsStatus(id)` to learn how the batch landed
on-chain.

## What's happening

1. The dapp calls `wallet_getCapabilities()`. The wallet
   declares per-chain capabilities — here it reports
   `atomic.status = "unsupported"` because the wallet
   sequences each call as its own EIP-1559 transaction.
2. The dapp calls `wallet_sendCalls([{ version, chainId,
   calls }])`. The wallet popup shows the N calls. On
   approval, the wallet signs each call as a separate
   EIP-1559 transaction, broadcasts them in order, stores
   `(batch_id → tx_hashes)` in extension session storage,
   and returns `{ id: batch_id }`.
3. The dapp polls `wallet_getCallsStatus([batch_id])`. The
   background script answers without re-opening the popup:
   it reads the batch registry, calls
   `eth_getTransactionReceipt` for each stored hash, and
   composes the spec response — status code, atomic flag,
   per-call receipts.

The dapp never has to track individual transactions — the
wallet is the source of truth for "did this batch succeed".

## The code

```ts
import { eip155_11155111 } from "@ethernauta/chain"
import {
  CALLS_STATUS,
  wallet_getCallsStatus,
  wallet_getCapabilities,
  wallet_sendCalls,
} from "@ethernauta/eip/5792"
import {
  create_signer,
  encode_chain_id,
  http,
} from "@ethernauta/transport"

const SEPOLIA_CHAIN_ID = encode_chain_id({
  namespace: "eip155",
  reference: eip155_11155111.chainId,
})
const SEPOLIA_CHAIN_REF_HEX = "0xaa36a7" as const

const signer = create_signer([
  {
    chainId: SEPOLIA_CHAIN_ID,
    transports: [
      http("https://ethereum-sepolia-rpc.publicnode.com"),
    ],
  },
])

// 1. (Optional) introspect what the connected wallet supports.
const capabilities = await wallet_getCapabilities()(
  signer({ chain_id: SEPOLIA_CHAIN_ID }),
)

// 2. Ask the wallet to send a batch. Returns immediately
//    with a batch id once the user approves; the wallet
//    sequences the calls behind the scenes.
const { id } = await wallet_sendCalls([
  {
    version: "2.0.0",
    chainId: SEPOLIA_CHAIN_REF_HEX,
    from: owner,
    atomicRequired: false,
    calls: [
      { to: "0x1111111111111111111111111111111111111111", value: "0x0", data: "0x" },
      { to: "0x2222222222222222222222222222222222222222", value: "0x0", data: "0x" },
    ],
  },
])(signer({ chain_id: SEPOLIA_CHAIN_ID }))

// 3. Poll for status. The wallet keeps the (id → tx_hashes)
//    map; this round-trip doesn't re-prompt the user.
const status = await wallet_getCallsStatus([id])(
  signer({ chain_id: SEPOLIA_CHAIN_ID }),
)
if (status.status === CALLS_STATUS.CONFIRMED) {
  // every receipt in status.receipts succeeded
}
```

## Status codes

| Code | Meaning |
|------|---------|
| 100  | Pending — at least one call still unmined |
| 200  | Confirmed — every call landed and succeeded |
| 400  | Failed offchain (wallet couldn't broadcast) |
| 500  | Reverted — every call reverted on-chain |
| 600  | Partially reverted — some calls reverted |

## What's next

The wallet currently broadcasts sequentially — each call is
its own type-2 tx. A follow-up will swap the strategy for
an atomic-via-7702 path (one type-4 tx delegating to the
`BatchExecutor` deployed in the EIP-7702 demo), and later
an atomic-via-4337 path (one UserOp). The dapp surface
stays identical — only the `atomic` flag in the status
response flips to `true`.
